## Where evidence and the founder's preferences pull apart

1. **"Glass-style backgrounds" versus Apple's own rule.** Apple says not to use Liquid Glass in the content layer and to use it sparingly, only on the most important controls and navigation (claims 3, 4). Glass as a general background or card style is the opposite of the platform owner's guidance. What Apple does endorse is glass on a floating tab bar, toolbar or sheet.
2. **Glass on the launch platform.** The first app is Android. Native Liquid Glass exists only on iOS 26+; on Android `expo-glass-effect` renders a plain View (claim 15). Any glass on Android is `expo-blur`, which is efficient only on Android 12+ and uses a much slower path below that (claim 16). The audience is on mid-range Android phones; the share of them below Android 12 was not measured in this run.
3. **Glass over product photos.** Apple's clear variant over bright imagery calls for a 35% dark dimming layer (claim 5), and `expo-blur` tints add a colour layer (claim 17). Both alter how the fabric underneath looks. For a shop where saree colour is the product, glass over the photograph works against colour fidelity. No source addressed sarees or fashion specifically; this is an inference from the platform guidance.
4. **Lavender versus contrast.** A light lavender cannot carry white button text or serve as text on white: at L 0.70 it reaches 2.77:1, well under 4.5:1; it needs to be about L 0.57 or darker, which reads as violet rather than lavender (claim 22). The pale lavender the founder likely pictures can be a surface or tint colour, with a darker violet as the working primary, or it can be a button fill with dark text.
5. **"No shadows anywhere" is compatible with both platforms, with two cautions.** Material's tonal surfaces and Apple's reported shift to borders support it (claims 9, 10, 13). Cautions: (a) shadcn components ship with shadow utility classes and there is no shadow token to switch off, so removal is a theme reset plus edits to component source (claims 27, 29); (b) native system components on iOS (sheets, glass bars) draw their own depth effects that the app does not control. Not verified in this run: whether Tailwind's focus `ring` utilities are implemented with box-shadow; if so, a blanket shadow ban must exempt focus indicators, which WCAG requires at 3:1.
6. **Carousels.** The founder wants carousels; NN/g and Baymard evidence is against auto-rotating ones and against putting must-see content only in a carousel (claim 36). Manually swiped rows and galleries are not contradicted; hidden slides and dot-only indicators are (claim 37).
7. **Micro-animations.** Welcome in moderation: Apple says to avoid motion on frequently repeated interactions and to make all motion optional; Reanimated disables animations under the system setting by default (claims 33, 34). Material's expressive springs overshoot, which Apple's reduce-motion guidance says to tighten.
8. **One token set for web and app.** shadcn on web is Tailwind v4 + OKLCH. On native, the stable NativeWind is still Tailwind v3 with HSL variables, and its v4-compatible version has been pre-release for 14 months (claims 30, 31). Sharing tokens exactly requires either Uniwind (stable, Tailwind v4, young), an RC dependency, or a build step that emits both formats. Whether OKLCH values resolve on native in each option was not verified.
9. **"Follow where Android is going".** Google's direction is Material 3 Expressive: bolder shape, colour and spring motion, with tonal surfaces. Frosted system surfaces in Android 17 are reported only by trade press (claim 14). Google has not published an Android glass material for apps that I could find.
10. **Coloured UI next to product photos.** Only weak practitioner evidence says neutral surrounds help colour judgement (claim 42). It points away from lavender-tinted backgrounds directly behind saree images, but the evidence is thin.

## Options for the design step

Presented, not chosen.

**Colour**
- A. *Two-step violet*: pale lavender (about L 0.92–0.96) for tinted surfaces and selected states; a darker violet (L ≤ 0.55) as the action colour with white text. Passes AA (claim 22). Trade-off: the brand "lavender" is not the button colour.
- B. *Lavender fill, dark text*: mid lavender (L 0.70–0.80) buttons with near-black text (6.5–8.7:1). Keeps lavender prominent. Trade-off: the button edge against white is under 3:1 unless it has a border; unusual look for a primary button.
- C. *Neutral UI, lavender as accent only*: neutral or shadcn "Mauve" base surfaces (claim 29), lavender limited to brand marks, focus and small highlights; photos always on neutral. Best for product colour fidelity (weak evidence). Trade-off: less distinctive.
- For all: define tokens in OKLCH as shadcn does, with light, dark and increased-contrast variants (claims 20, 29).

**Type**
- A. *Platform system fonts in the app, one web font on the site* (system fonts carry Dynamic Type and Indic coverage automatically; claim 24). Trade-off: brand differs between web and app.
- B. *Noto Sans + Noto Sans Tamil/Telugu/Kannada/Malayalam* variable, OFL (claim 40). Conservative, broad coverage. Trade-off: four extra script files; neutral personality.
- C. *Anek* variable multi-script family, OFL, shared design across scripts, weight and width axes (claim 40). More distinctive. Trade-off: display-leaning; Telugu coverage needs checking; body-text legibility at 12–14 px untested here.
- Scale anchors with evidence: body 16–17, minimum 11–12, line-height about 1.3–1.5, support 200% enlargement (claims 24, 25, 26).

**Spacing**
- A. *4 px base* (Tailwind's `--spacing: 0.25rem`), using the 4/8/12/16/24/32 steps (claim 26). Maps directly to web utilities and, with `inlineRem: 16`, to native (claim 30).
- B. *8 px base with a 4 px half-step*. Fewer choices, stricter rhythm. Trade-off: needs a restricted custom scale on top of Tailwind.
- Fixed constraints either way: 44 pt / 48 dp targets, 8 dp between targets, 12–24 pt padding around controls (claim 23). No source in this run compared 4 against 8.

**Radius**
- A. *shadcn default*: one `--radius` of 0.625rem (10 px) deriving the whole scale (claim 29). Least work.
- B. *Larger, softer base* (16 px or more, pill buttons), in line with M3 Expressive's rounder shapes (claims 11, 14; thinly sourced). Trade-off: rounded corners crop product photo edges.
- C. *Small radius on images, larger on controls*. Protects photos; two rules to maintain.

**Depth without shadow**
- A. *Tonal surfaces* (Material's surface-container ladder; claim 13): three to five lightness steps of the neutral or lavender-tinted surface. Trade-off: tinted steps next to photos (see conflict 10); steps must stay distinguishable in dark mode.
- B. *Hairline borders and rings* (Linear, Geist; claim 43). Crisp, cheap to render. Trade-off: borders on every card can look busy in a dense grid; needs 3:1 where the border is the only cue for a control (claim 21).
- C. *Scrim and scroll-edge fade for overlays* plus spacing and scale for hierarchy (claim 9). Trade-off: sheets and menus over white content need a scrim or border to separate at all.
- These combine; the decision is which is primary.

**Glass**
- A. *None on Android and web; native glass on iOS later* through system components (claims 3, 15). Cheapest and safest on mid-range phones. Trade-off: founder's stated direction not visible at launch.
- B. *Glass on chrome only*: bottom tab bar, top bar on scroll, sticky purchase bar; regular (frosted) variant, never over the main product image; Android 12+ only via `dimezisBlurViewSdk31Plus`, with a solid or tonal fallback below that and under Reduce Transparency; web `backdrop-filter` behind `@supports` with an opaque fallback (claims 5, 16, 18). Trade-off: one blur layer redrawn during scroll, which is the costly case; needs testing on real target phones.
- C. *Glass as a broad surface style* (cards, sheets, banners). Contradicts Apple's guidance and carries the highest performance and legibility risk (claims 3, 4, 18, 19).

**Motion**
- A. *CSS and platform defaults only*: CSS transitions and same-document view transitions on web (claim 35), Reanimated layout and timing on native. Smallest bundle.
- B. *Motion 14 on web + Reanimated 4.7.1 on native* with one shared set of duration and easing or spring tokens (claims 32, 33). Trade-off: extra JavaScript on web on 4G.
- C. *Add Lottie or Rive for a few set pieces* (order placed, empty states); both current (Versions). Trade-off: asset weight; another runtime.
- Moti is not a current option on the evidence (no release since 2025-01). All options: honour reduced motion, keep feedback brief, no animation on high-frequency actions (claim 34). Official Material duration and easing values were not retrieved.

**Web stack**
- A. *shadcn 4.23 + Tailwind 4.3 + Next 16 + React 19*: current, mutually compatible, OKLCH variables, founder-approved (claims 26–29). Shadows removed by clearing the shadow theme namespaces (inference) and editing component classes.
- B. *Tailwind 4 with hand-built components on headless primitives*. Full control over the no-shadow rule. Trade-off: more build time.
- C. *A cross-platform kit on web too* (Tamagui 3.3). One component set for web and app. Trade-off: leaves the shadcn ecosystem; own compiler and token system.

**Native stack**
- A. *Uniwind 1.14 + react-native-reusables*: stable release, Tailwind v4, same `@theme` approach as web, shadcn-style components (claims 30; Versions). Trade-off: Uniwind is 16 months old; SDK 58 compatibility inferred from peer ranges, not from a published statement.
- B. *NativeWind 4.2.7 + react-native-reusables*: longest track record. Trade-off: Tailwind v3 config and HSL variables on native while web is v4 and OKLCH, so tokens are generated twice; SDK 58 testing not confirmed.
- C. *NativeWind 5 RC (optionally gluestack-ui v5)*: Tailwind v4 parity. Trade-off: release candidate, tested by its authors on Expo 57 / RN 0.86.
- D. *Unistyles 3.9 or Tamagui 3.3 with tokens exported from one source file*: both released this month, RN 0.88 within peer ranges. Trade-off: not Tailwind class names, so no shared component code with shadcn; Unistyles needs Nitro modules.
